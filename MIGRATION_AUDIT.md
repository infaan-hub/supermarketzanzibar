## 2. Backend facts (Django 6.0.1 target / DRF 3.16 / SimpleJWT 5.5)

### 2.1 Database
* **Production database: Neon PostgreSQL** (`DATABASE_URL` in settings, also pinned in
  `render.yaml`). SQLite is explicitly *disabled* by settings (`ImproperlyConfigured` if
  `DATABASE_URL` starts with `sqlite`). A local `zansupermarket\db.sqlite3` also exists with
  **development data** (8 users, 5 sales/payments/stock movements, 2 products, 2 categories)
  — it is not used by the deployed backend but is preserved as a backup.
* Engine confirmed by live inspection: **PostgreSQL**, schema `public`, tables named
  `supermarketzanzibar_*` + Django system tables.
* All primary keys: `bigint GENERATED BY DEFAULT AS IDENTITY` (Django `BigAutoField`).
* Monetary columns: `numeric(10,2)` / `numeric(12,2)` (exact decimals).
* Timestamps: `timestamp with time zone`, `TIME_ZONE=UTC`, `USE_TZ=True`.
* Images/proofs: stored **in the database as `bytea`** (see §4), not on disk.
* Constraints (verified): unique `customuser.username`, `customuser.email`,
  `customuser.phone`, `customer.user_id`, `supplier.user_id`, `product.barcode`,
  `product.slug`, `payment.sale_id`, `payment.control_number`. **No unique constraint on
  `category.name`.** FKs are `DEFERRABLE INITIALLY DEFERRED` (Django default).
* Production row counts (audited): users 4, categories 7, customers 1, suppliers 1,
  products 8, sales 0, sale items 0, payments 0, stock movements 0.

### 2.2 Authentication / JWT (SimpleJWT)
* `ACCESS_TOKEN_LIFETIME=30min`, `REFRESH_TOKEN_LIFETIME=7days`,
  `ROTATE_REFRESH_TOKENS=True`, `BLACKLIST_AFTER_ROTATION=False`.
* **No blacklist/outstanding-token tables exist** → refresh tokens are stateless; a rotated
  refresh token remains technically valid until its `exp` (original semantics preserved).
* No logout endpoint exists in the original API (frontend logout only clears storage).
* Default DRF permission = `IsAuthenticated`; authentication = Bearer access token.
* Passwords: Django PBKDF2 (`pbkdf2_sha256$iterations$salt$hash`, iterations embedded in the
  stored hash). Google-created accounts use Django's *unusable* marker (`!…`) and can only
  log in through Google.
* Response contracts:
  * login/Google login → `{refresh, access, user}` (user = full UserSerializer payload)
  * refresh → `{access, refresh}` (refresh present because rotation is enabled)
  * invalid/expired token → `401 {"detail": "Given token not valid for any token type",
    "code": "token_not_valid", "messages": [{token_class, token_type, message}]}`
  * missing credentials → `401 {"detail": "Authentication credentials were not provided."}`
  * insufficient permission → `403 {"detail": "You do not have permission to perform this action."}`
* Google login verifies the ID token against `https://oauth2.googleapis.com/tokeninfo?id_token=…`
  and requires `aud == GOOGLE_CLIENT_ID` and a verified email.

### 2.3 Scheduled access (`access_window_start/end`, migration 0011)
* Applies only to roles `supplier` and `driver` (`SCHEDULED_ACCESS_ROLES`).
* Active iff `start <= now < end` (UTC). Both null → not scheduled → **denied**.
* Enforced at: role login (supplier/driver), `GET/PATCH /api/auth/me/`, and the permission
  classes of supplier dashboard/alerts and all three driver endpoints.
* **Not** enforced on generic `IsAuthenticated` endpoints (e.g. product create) and **not**
  on `IsAdminOrSupplierRole` (payment confirm) — original behavior, preserved.
* Denial messages differ for “not scheduled yet”, “starts at …”, “ended at …”
  (formatted `YYYY-MM-DD HH:MM:SS UTC`).
* `GET /api/auth/schedule-task/` lists supplier+driver users ordered by
  `role, full_name, username`; `PATCH …/{user_id}/` accepts `access_window_start/end`
  (ISO strings or `null`), requires both-or-neither and `end > start`.

### 2.4 API surface — router and permissions (from `supermarketzanzibar/urls.py` + `views.py`)
* DRF `DefaultRouter` resources: `users, categories, suppliers, customers, products, sales,
  sale-items, stock, payments` + API root at `/api/`. **No pagination configured** → list
  endpoints return plain JSON arrays.
* `ProductViewSet.get_permissions()`: list/retrieve/image → AllowAny; create/update/
  partial_update/destroy → IsAuthenticated, then `perform_create/update/destroy` enforce
  admin-or-supplier with **ownership check** (suppliers only manage their own products;
  supplier create forces `supplier` FK to their own profile). Retrieve accepts numeric pk
  **or slug**.
* `SaleViewSet`: list/retrieve → IsAuthenticated with role scoping (admin all; driver →
  assigned; customer → own `sale.user`; supplier → none). create/update/DELETE/
  `assign_driver` → admin only. `assign_driver` validates `driver_id` is a `role=driver`
  user (else 404 “Driver not found.”), sets `assigned_driver`, and bumps
  `payment_confirmed|processing → out_for_delivery`.
* `PaymentViewSet`: list/detail scoped (admin all; customer own sales' payments; others none);
  `confirm` action → admin **or** supplier, supplier limited to payments containing their
  products (404 otherwise); already-confirmed → 200 idempotent; non-pending → 409
  “Only pending payments can be confirmed.”; confirm sets `sale.payment_confirmed=True`,
  `pending_payment → payment_confirmed`, auto-assigns sole driver, sends email (fail-silent).
  `admin_pending` → admin only, serializer = PaymentAdminSerializer (nested items + customer
  snapshot).
* `SaleItemViewSet` / `StockViewSet`: `IsAuthenticated` only, **no queryset scoping** in the
  original (see §7 security deviations). Stock = `StockMovement` audit rows; creating a
  movement does **not** adjust `product.quantity` (only checkout and product CRUD do).
* Users/Suppliers/Customers viewsets: admin only. `UserSerializer` has `role`,
  `access_window_*` **read-only** → role escalation via `/api/users/{id}` was already
  impossible.
* Category CRUD: any authenticated user, no extra business constraints (name not unique).
* Public product list uses `PublicProductSerializer` (only id/name/slug/price/quantity/
  image/image_url/description/category_name/updated_at) — the **full** `ProductSerializer`
  (with `cost_price`, `barcode`, `supplier`, `is_active`, timestamps) is used for detail,
  mutations, supplier dashboard, and admin.

### 2.5 Checkout (critical flow, `CheckoutView`)
* Customer-only. `@transaction.atomic`, `SELECT … FOR UPDATE` on products.
* Server computes totals from DB prices (`product.price * qty`), stock check
  (`product.quantity < qty` → 400 “Not enough stock for X.”), missing product → 400,
  empty cart → 400 “Cart is empty.”.
* Creates `Sale` (status `payment_confirmed`, `payment_confirmed=True`, tax/discount 0,
  customer snapshot fields, `final_amount = total − discount + tax`), `SaleItem` rows
  (total recomputed in model `save`), decrements `product.quantity`, inserts `StockMovement`
  (`OUT`), creates `Payment` **already `confirmed`** (control number auto-generated
  `ZNyymmdd` + 8 digits), auto-assigns sole driver, sends email (fail-silent), returns
  `{sale, payment, whatsapp_url}` **201**.
* No idempotency mechanism existed (see §7 for the added retry-dedupe).

### 2.6 Receipts, images, barcodes
* `GET /api/customer/orders/{id}/receipt/` → PDF (`application/pdf`,
  `attachment; filename="receipt-order-{id}.pdf"`), only when a confirmed payment exists
  (409 otherwise, 404 for foreign/missing orders). Generated with ReportLab: A4, palette
  `#edf6ee/#1f8f3a/#15722d`, sections “OFFICIAL CUSTOMER RECEIPT”, “Payment Confirmed”,
  “CUSTOMER & ORDER DETAILS”, “PAYMENT”, “PAID PRODUCTS”, “ABOUT US”, “CONTACT US”.
  (An unstyled fallback PDF generator also exists.) Product thumbnails inside the receipt
  are always the “PRODUCT IMAGE UNAVAILABLE” placeholder because the old `image` FileField
  was removed in migration 0006 — preserved as-is.
* `GET /api/products/{id}/image/` → bytes from DB with original content type,
  `Content-Disposition: inline`, `Content-Length`, `Cache-Control: public, max-age=86400`,
  404 `{"detail": "Product image not found."}` when absent.
* Payment payloads embed `barcode_image_url` (Code128 PNG data URL of the control number’s
  digits) and `proof_image_url`/`profile_image_url` as base64 data URLs.

### 2.7 Product image upload pipeline (models.py)
* Output is always **JPEG ≤ 1 MiB**: EXIF-transpose → RGB (alpha flattened to white) →
  thumbnail max dimension 1600 → quality ladder (85…30) → if still >1 MiB, iterative downscale
  (factor from size ratio, floor 96px min dimension). Stored as `{stem}.jpg` /
  `image/jpeg`. Input validated by decoding with Pillow (rejects non-images; default
  decompression-bomb limits apply). No explicit input-size cap existed.
* Profile/payment-proof images: decode → RGB → JPEG quality 90.

### 2.8 Misc backend
* `zansupermarket/middleware.py`: CORS fallback that answers OPTIONS preflight for allowed
  origins and echoes CORS headers on `/api/*`. With a single same-origin app this is no
  longer needed (removed, documented here).
* `send_mail` on checkout and payment confirmation; SMTP only when `EMAIL_HOST` is set,
  otherwise console backend (fail-silent either way).
* Django admin site at `/admin/` (registers user/category/supplier/customer/product/sale/
  saleitem/stockmovement). It is replaced by the Next.js admin dashboard + `/api` CRUD; no
  HTML admin site is recreated (not part of the required route table).
* Error style: DB/storage failures are mapped to `503 {"detail": …}` messages per view;
  validation errors are DRF field maps `{"field": ["msg"]}` (400).

## 3. Frontend facts (React 19 + Vite 7 + react-router-dom 7 + axios)

* Routes (all preserved): `/`, `/home`, `/search`, `/filter`, `/category`, `/login`,
  `/admin/login`, `/supplier/login`, `/driver/login`, `/register`, `/admin/register`,
  `/products/:id`, `/cart`, `/payment`, `/profile`, `/customer/dashboard`,
  `/admin/dashboard`, `/schedule-task`, `/supplier/dashboard`,
  `/supplier/dashboard/scan`, `/supplier/calculator`, `/driver/dashboard`,
  `*` → redirect `/home`.
* Root redirect: guest → `/home`; admin → `/admin/dashboard`; supplier →
  `/supplier/dashboard`; driver → `/driver/dashboard`; any other authenticated user →
  `/customer/dashboard`.
* Guards (`RoleRoute`): unauthenticated → role login page (single-role list) or `/login`;
  wrong role → `/home`. Guard state is **client-side only** (tokens live in
  `localStorage`: `ss_access_token`, `ss_refresh_token`).
* API client: axios, base URL from `VITE_API_BASE_URL` (fallback `127.0.0.1:8000` dev /
  `https://supermarketzanzibar.onrender.com` prod) → becomes same-origin `/api`.
  Behaviors preserved: Bearer header injection; single retry of **network-failed GETs**
  after 1.2 s; on 401 → one refresh attempt (`POST /api/auth/token/refresh/`) then retry the
  original request once; 401/403 on `/api/supplier/`, `/api/driver/`, `/api/auth/me/` →
  immediately clear tokens (force re-login); refresh failure → clear tokens. Auth context
  additionally retries auth POSTs once on network error (1.5 s) and force-logs-out
  supplier/driver users when `access_window_end` passes (plus 30 s / focus polling of
  `/api/auth/me/`).
* Note: concurrent 401s could previously trigger **competing refreshes**; the master prompt
  requires single-flight refresh — implemented in the new client.
* Images: `toMediaUrl()` prefixes the API base; placeholder SVGs + `data-fallback-src`
  onError fallback.
* Supplier scanner: `BarcodeDetector` when available, otherwise `@zxing/browser`
  (`BrowserMultiFormatReader`) for camera/receipt-image/manual code matching against
  `supplier/dashboard` products (barcode/slug/id/name/URL candidates).
* Payment page: entirely client-side card/wallet form (card number/expiry/CVV/PayPal
  email/Yas Mixx number are **never sent to the backend** — only
  `items, payment_method, customer_*, delivery_location, terms_accepted` go to checkout);
  success screen renders a canvas receipt (uses `payment.barcode_image_url`); cart snapshot
  taken at load; no stock re-validation client-side.
* Styling: single 63 KB `src/index.css` (Google Fonts import `DM Sans`/`Outfit`, CSS
  variables, light/dark `data-theme`), class-name driven; theme persisted in
  `localStorage["theme-mode"]`. No Tailwind/component library.
* Assets: `src/assets/*` (payment brand JPGs, placeholders, visa svg) + `/vite.svg` favicon.
* **Dead code found** (not migrated): `leaflet`, `react-leaflet`,
  `leaflet/dist/leaflet.css` import, `src/data/zanzibarRoutes.*` (nothing imports them).

## 7. Deliberate deviations (security requirements of the master prompt)

These are the only places where the new implementation intentionally differs from the
original behavior; everything else is a faithful port. Each is covered by tests.

1. **Admin registration** (`POST /api/auth/admin/register/`) was fully public and created
   `role=admin` accounts. Now allowed **only while zero admin accounts exist** (bootstrap of
   the “First admin?” flow); afterwards `403`. Customer registration can never set `role`
   (read-only in the original too).
2. **Payment writes**: `POST /api/payments/` no longer accepts `status != "pending"` from
   non-admin clients and requires the payment’s `sale` to belong to the caller (admins
   exempt). `PATCH/PUT /api/payments/{id}`: non-admins may update their own payment’s
   proof/method but **not** `status`/`confirmed_by` (status transitions stay with the
   `confirm` action). Prevents “payment status tampering”.
3. **Sale items**: reads scoped to records the caller may see (admin all; customer → own
   sales; driver → assigned sales; supplier → sales containing their products);
   create/update/delete restricted to admin (mirrors the admin-only sale mutations and
   keeps sale totals consistent).
4. **Auth rate limiting**: in-memory sliding-window limiter on login/register endpoints
   (per IP). Limitation: per-process state, resets on cold start (documented).
5. **Checkout idempotency**: identical checkout retries from the same customer within a
   10-second window return the original `{sale, payment, whatsapp_url}` payload instead of
   creating a duplicate sale/decrementing stock twice.
6. **Refresh token storage for browsers**: the JSON body still returns `refresh`
   (contract preserved for API consumers), but the browser client stores the refresh token
   **only in an HttpOnly, SameSite=Lax cookie** scoped to the refresh endpoint. Access
   token stays in `localStorage` so the original `Authorization: Bearer` contract is
   unchanged. No CSRF exposure: state-changing APIs trust only Bearer tokens.
7. **Upload hardening**: product/profile/proof uploads are rejected above a 10 MiB input
   limit with pixel-count guards (the original relied on Pillow defaults only); magic-byte
   validation is required before decode. Filename generation was already safe (stem +
   fixed `.jpg`) and is preserved.
